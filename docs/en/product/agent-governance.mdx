Locus is built for sustained use, not one-off Q&A. That's why models, rules, tool confirmation, and runtime visibility are split out into a dedicated governance layer.

## Current Governance Capabilities

- Multi-model access: OpenRouter, Claude subscription, Claude Agent SDK, OpenAI Codex, custom endpoints
- Plan mode and Build mode
- Sub-agent / `subagent` tool
- Tool execution confirmation, with batch confirm
- Per-round undo tracking for file changes
- Raw context export
- A visual dashboard for the Agent's system prompt, env, rules, runtime injections, and tool schemas
- Agents can add, update, and toggle workspace rules through the Python SDK without opening settings

## Built-in Agents

| Agent | Purpose | Default for |
|---|---|---|
| Unity (`unity`) | Unity project development, debugging, and optimization, with Editor, asset, test, and C# code tools | Unity workspaces |
| General (`general`) | General software development with knowledge, Skills, todos, questions, web fetch, View/Workbench control, and the Python SDK, without Unity tools or rules | Non-Unity workspaces |
| Simple (`simple`) | Minimal Agent with file, shell, Python, and search tools | Manual selection |

Subagents do not appear in the new-session Agent list. Unity delegates to Explorer (`explorer`) for code, asset, and live Unity research; General delegates to Researcher (`researcher`) for read-only research across workspace files, project knowledge, and external documentation. The `subagent` tool lists only Agents that support the current workspace type, and General is never offered as a subagent.

## Workspace Rules

Select the built-in Agent with `await locus.get_agent("unity")` (or `"general"` in a non-Unity workspace). Use `list_rules()` to inspect rules, `read_rule(key)` to read Markdown, `save_rule(file_name, content)` to add or update a rule, and `set_rule_enabled(key, False)` to disable one. Pass `True` to re-enable it.

The SDK defaults to the Python session's checkout and also accepts `workspace_ref=` or `worktree=`. Rule content and enablement are stored under that workspace's `Locus/agent/<agent-id>/`. Editing an inherited rule creates a workspace override; installed defaults and other workspaces stay unchanged. Changes appear in the existing Agent rule list and apply on the next model request, including the current run's next tool round.

## What This Solves

- Lets teams shape the Agent's default behavior and boundaries
- Keeps tool calls and file changes reviewable and reversible
- Makes model selection, rule injection, and context composition transparent over the long haul

## Teams It Fits Best

- Already running multiple models in parallel
- Need to inspect what the Agent is actually doing
- Want rules and knowledge to live in a stable governance flow
